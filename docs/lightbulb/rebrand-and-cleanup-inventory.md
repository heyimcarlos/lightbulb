# Lightbulb Rebrand and Cleanup Inventory

- Issue: #43

- Scope: read-only inventory plus follow-up slicing. No runtime, package, binary, storage, or README behavior changes are made by this document.

## Classification Rules

Lightbulb should treat OpenCode names in two different buckets:

- Public product identity: names shown to users as the product, install target, repository, website, app, extension, action, package, or community. These should become Lightbulb in staged follow-up slices.
- Substrate compatibility identity: names that existing runtime state, upstream mergeability, imports, generated clients, provider contracts, env vars, storage paths, or package resolution depend on. These should be preserved until an explicit compatibility slice adds aliases, migrations, and rollback checks.

Decision values use the issue vocabulary:

- keep: leave as-is because the OpenCode reference is intentional substrate or historical context.
- remove: delete in a future cleanup slice after verification.
- rename: change public identity to Lightbulb in a future rebrand slice.
- alias: add Lightbulb-facing names while keeping OpenCode compatibility names.
- defer: postpone until another slice decides the owning product boundary.
- needs-human: require maintainer approval before the action is safe for an AFK agent.

## Proposed Ordered Migration Sequence for the `lightbulb` Binary

1. Human decision: choose distribution names and compatibility policy. Decide npm package name, GitHub release repo, Homebrew tap, Docker image, Nix package, VS Code extension identity, GitHub Action name, install URL, and whether `opencode` remains indefinitely as an alias.
2. Add an additive local command alias. In `packages/opencode/package.json`, expose `lightbulb` alongside `opencode` and teach the wrapper/entrypoint to infer display name from the invoked executable. Keep `packages/opencode` as the package path and keep `opencode` runnable.
3. Preserve env and storage compatibility. Add `LIGHTBULB_*` reads only where needed, with `OPENCODE_*` fallback and explicit precedence. Do not move XDG or `~/.opencode` storage in this step.
4. Update user-facing docs to make `lightbulb` primary. Root README, install examples, help text, and public docs should show `lightbulb`, with a compatibility note for `opencode`.
5. Update build artifacts additively. Produce release archives/packages that contain `lightbulb` as the primary executable and retain `opencode` as a shim or alias. Verify npm, single-binary build, and install script behavior before changing external package managers.
6. Retarget distribution channels. Update GitHub releases, install script, Homebrew, AUR, Nix, Docker, GitHub Action, and VS Code extension after the binary alias works locally and in CI.
7. Plan storage migration separately. Only after command/distribution migration is stable, decide whether to migrate `~/.config/opencode`, `~/.local/share/opencode`, `~/.cache/opencode`, `~/.local/state/opencode`, and `~/.opencode/bin` into Lightbulb paths. That slice needs seeded old-state tests and rollback notes.
8. Revisit package namespace last. Rename `@opencode-ai/*` only after upstream mergeability is no longer a priority or a compatibility facade exists.

Minimum verification for the binary alias slice:

- `bun --cwd packages/opencode typecheck`
- `bun --cwd packages/opencode build --single --skip-embed-web-ui`
- `./packages/opencode/dist/<platform>/bin/lightbulb --help` shows Lightbulb command name.
- `./packages/opencode/dist/<platform>/bin/opencode --help` still works.
- A seeded `OPENCODE_CONFIG_CONTENT` run still behaves as before.
- A seeded `LIGHTBULB_CONFIG_CONTENT` run follows the documented precedence only after env aliases exist.

## Intentional `opencode` / `OpenCode` Allowlist After the First Rebrand Pass

Keep these references after the first public-product README/repository metadata pass:

- `docs/lightbulb/**` references that describe OpenCode as the fork, upstream, execution substrate, session shell, provider/session runtime, or schema boundary.
- `@opencode-ai/*` package names, imports, exports, service identifiers, and workspace dependencies.
- `packages/opencode/**` path references and package name references until the runtime path compatibility issue says otherwise.
- `opencode` command references that are explicitly compatibility aliases after `lightbulb` is primary.
- `OPENCODE_*` env vars, `x-opencode-*` HTTP headers, `OpencodeClient`, and generated SDK names until an API compatibility plan exists.
- `.opencode/**`, `opencode.json`, `opencode.jsonc`, `~/.config/opencode`, `~/.local/share/opencode`, `~/.cache/opencode`, `~/.local/state/opencode`, and `~/.opencode/bin` until config/storage aliases and migrations exist.
- `opencode.ai` schema URLs in config/theme files until schema hosting is replaced or mirrored.
- Patch file headers, lockfile entries, generated code, and vendored comments that preserve build provenance.
- Upstream comparison/history links such as `anomalyco/opencode` in ADRs or docs that intentionally document fork lineage.
- Inherited optional packages under `packages/console/**`, `packages/stats/**`, `packages/slack/**`, `packages/desktop/**`, `packages/web/**`, and `packages/enterprise/**` until their owning cleanup issues decide keep/remove.

Do not allow these after the first public rebrand pass unless the follow-up issue explicitly defers them:

- Root README statements that say the repository is OpenCode.
- Root README install commands that install upstream OpenCode for Lightbulb users.
- Root `package.json` repository metadata pointing at `anomalyco/opencode`.
- Public action, extension, desktop, website, or package descriptions that present Lightbulb releases as upstream OpenCode releases.

## Agent-Safe Follow-Up Slices

These can be routed to AFK agents once opened as bounded issues:

- `repo-metadata-rebrand`: change root private package name and repository URL, then verify install metadata.
- `docs-rebrand-readmes`: rewrite `README.md` as Lightbulb-first and either link or explicitly defer localized READMEs.
- `opencode-config-retarget`: inspect disabled `.opencode/tool/**` and agent command files, retarget safe Lightbulb repo references, and keep config path unchanged.
- `lightbulb-bin-alias`: add an additive binary alias without moving storage or renaming package namespaces.

These require maintainer approval before an AFK agent should implement:

- `workspace-namespace-adr`: whether to rename `@opencode-ai/*` packages.
- `storage-env-compat-adr`: whether and how to introduce `LIGHTBULB_*` env vars and Lightbulb storage paths.
- `distribution-rebrand-plan`: release channels, npm, Docker, Nix, Homebrew, AUR, install script, and GitHub releases.
- `github-action-rebrand`: action name, trigger phrases, GitHub App identity, token exchange endpoint, and release channel.
- `optional-packages-prune`: remove or retain console, stats, Slack, enterprise, web/docs, function, and desktop surfaces for Lightbulb v0.
- `localized-readme-policy`: translate, remove, archive, or replace localized root READMEs.
