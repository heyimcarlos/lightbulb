Traceable Loop Runtime Spine

Implementation plan for turning the paused cron-style Lightbulb loops into a durable goal, loop, run, worker, gate, and artifact control plane.

Status: ready for implementation thread Base: origin/dev plus merged PR #57 Top task 1 Prepared: 2026-06-22

Architecture Theories Reviewed

Theory What It Optimizes Failure Mode Decision
Archaeology first Recover all old worker branches and merge their outputs in dependency order. Unavailable worktrees, stale assumptions, broad file overlap, and weak current verification. Reject as the primary route. Use old reports only as comparison evidence.
UI first Make the desktop/dashboard feel like the finished loop control plane. Pretty status over weak durable state. The app would display state that the runtime cannot yet enforce. Defer until after the runtime spine exposes stable read models.
Deterministic spine first Land the smallest durable state machine that every later loop can reuse. May feel less complete because it does not launch real model processes yet. Choose this. It directly fixes traceability and gives UI/workers a stable substrate.

Target Runtime Shape

GoalOne durable destination with owner intent and stop conditions.
LoopRecurring profile with schedule, budget, policy, and next due time.
AdmissionTransaction creates one queued run or one skipped event.
Task PacketBounded child instructions, issue/work item, context budget, expected artifacts.
Launch AttemptProcess/session/worktree/log/report handles and idempotent active key.
GateReview, debug, budget, dependency, or human approval state.
ArtifactReport, evidence, patch, test result, screenshot, or PR handle.

Detailed Steps For PR A

1. Clean boundary
Inspect the diff and separate unrelated files. Keep the migration fix, run ledger, scheduler tick, worker launch attempt, dashboard/CLI read model, and the browser test fix only if this PR owns it. Move planning artifacts to docs or leave them untracked until PR B.
2. Normalize semantics
Make skipped admission and held launch behavior explicit. A skipped event must never create a duplicate run. A held launch may block parent-facing worker/task state only when the input explicitly requests a blocked terminal launch; otherwise it should remain a skipped launch request with the exact hold reason.
3. Migration audit
Verify the generated schema and migration order. The existing artifact-edge migration fix must stay because it prevents SQLite foreign-key mismatch during desktop database startup.
4. Operator readback
Keep the text dashboard useful for triage: operations section for scheduler ticks, launch attempts under workers, and JSON parity. Avoid adopting PR #56's compact dashboard in the same PR unless it is consciously reconciled.
5. Evidence packet
Write a small HTML or markdown evidence packet under .lightbulb/evidence/pr-<number>/ after a PR exists. Include the seeded dashboard command output and a screenshot of the HTML evidence or app dashboard.

Review Rounds

Round Reviewer Focus Exit Criteria
Round 1 Runtime correctness: idempotency, transaction boundaries, skip reasons, migration safety. No duplicate active run/launch records; all skipped/no-op decisions leave durable events.
Round 2 Traceability: every operator-visible row links to account, goal, loop, run, worker, packet, or artifact. Parent summary and dashboard can explain what happened without reading raw worker transcripts.
Round 3 PR readiness: diff boundary, tests, docs, visual evidence, no stale worker branch cargo. PR is small enough to review and can be merged without forcing PR #56 or #55 to land first.
